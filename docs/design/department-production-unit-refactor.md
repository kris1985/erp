# 生产组织重构：子部门即生产分组，移除班组实体

> **状态：** 方案已确认，待实现  
> **日期：** 2026-08-28  
> **范围：** 生产组织、段级派工、报工权限、集体报工、工资归属、组长工作台  
> **核心决策：** 只保留一棵 `Department` 组织树；需要细分时，以生产部门的子部门作为生产组，不再维护 `Team` / `TeamMember`。

---

## 1. 背景

当前系统同时维护两套生产组织：

- `Department`：员工的正式组织归属，挂工序段和负责人；
- `Team` / `TeamMember`：段级派工、报工范围和组长工作台使用；
- 无班组模式仍会为每个生产部门生成一个 `is_default=true` 的隐形默认组；
- 派工页面直接读取 `/teams`，导致隐形组、测试组与部门同时出现，名称和数量无法对应。

这套模型造成四类问题：

1. 同一个生产单元要在部门和班组中维护两次；
2. 员工调部门后还要同步班组成员，容易产生脏数据；
3. 单组部门也被迫生成“裁断组、包装组”之类无业务价值的占位对象；
4. 派工、报工、权限分别依赖不同组织对象，用户难以理解。

本次重构统一为：

```text
生产部
├─ 裁断部                    # 无细分，直接派给裁断部
├─ 针车部                    # 汇总部门
│  ├─ 针车一组               # 子部门，实际派工单元
│  └─ 针车二组               # 子部门，实际派工单元
├─ 成型部                    # 无细分，直接派给成型部
└─ 包装部                    # 无细分，直接派给包装部
```

---

## 2. 设计目标

- 员工只维护一个 `department_id`，不再维护班组成员关系；
- 工序段与生产部门建立稳定映射；
- 无子组时直接派到生产部门；有子组时派到一个或多个子部门；
- 报工事实始终记录实际员工，计件工资不记到部门；
- 父部门负责汇总，末级生产部门负责执行；
- 历史派工、报工和工资在迁移过程中不断链；
- 最终从模型、接口、权限和界面中删除班组概念。

## 3. 不在本次范围

- 一个员工同时长期属于多个生产组；
- 按白班、夜班建立排班体系；
- 临时项目组、跨部门虚拟团队；
- 改造计件单价、工资锁价和月结算法；
- 改造工位、捆、色码等细粒度派工模型；
- 企微或钉钉组织同步。

临时跨组支援继续使用现有个人细派能力或在集体报工时选择实际参与人，不为此恢复长期班组实体。

---

## 4. 术语与不变量

### 4.1 术语

- **工序段 `ProcessSegment`**：裁断、针车、成型、包装、铲皮等生产阶段；负责工艺归类和统计。
- **生产部门**：挂有工序段、参与生产执行的部门，例如针车部。
- **生产组**：生产部门下面用于独立接单的子部门，例如针车一组；仍然是 `Department` 记录。
- **派工单元**：当前工序段可选择的最末级启用生产部门。
- **实际报工人**：产生 `WorkLog` 和计件工资的员工。

### 4.2 不变量

1. 每个员工最多只有一个当前 `department_id`；
2. 一个生产子部门与父生产部门必须属于同一工序段；
3. 一个工序可以派给多个部门；
4. 同一个段级派工提交中，不允许混入其他工序段的部门；
5. 父部门被派工时，其所有启用后代部门员工均在范围内；
6. 子部门被派工时，只允许该子部门及其后代员工报工；
7. 报工和工资始终落到员工，不允许只记部门产量而没有实际人员；
8. 历史报工使用部门快照，不因员工后续调部门而改变；
9. 生产主路径不再创建、修改或读取 `Team` / `TeamMember`。

## 5. 目标数据模型

### 5.1 Department

保留现有字段：

```text
departments
├─ id
├─ tenant_id
├─ name
├─ parent_id
├─ process_segment_id
├─ manager_employee_id
├─ production_leader_id
├─ sort_order
└─ is_active
```

新增：

```text
is_production_unit BOOLEAN NOT NULL DEFAULT FALSE
```

语义：

- `false`：普通行政部门，不参与生产派工候选；
- `true`：生产组织节点，可挂工序段并参与执行；
- 生产父部门和生产子部门都可以为 `true`；
- 实际派工候选通过“最末级生产节点”计算，不依赖人工切换父部门状态。

人员职责字段严格分开：

- `manager_employee_id`：部门负责人/车间主管，负责管理、派工、查看汇总，可以不参与生产报工；
- `production_leader_id`：生产组长/带班人，必须是该生产部门的在职生产员工，既参与现场生产，也负责本组报工与人员协作；
- 两个字段允许是不同员工，不自动互相同步；
- 现有 `leader_id` 迁移并重命名为 `production_leader_id`，删除“部门负责人自动同步为默认组组长”的旧逻辑。

典型结构：

```text
针车部
├─ 部门负责人：针车主管（只管理）
├─ 针车一组
│  └─ 生产组长：王师傅（本组员工，参与报工）
└─ 针车二组
   └─ 生产组长：李师傅（本组员工，参与报工）
```

没有子组的生产部门也可以同时配置两个不同的人：

```text
裁断部
├─ 部门负责人：裁断主管
└─ 生产组长：张师傅
```

创建生产子部门时：

- 必须选择一个生产父部门；
- 自动继承父部门 `process_segment_id`，界面只读；
- 不允许改成与父部门不同的工序段；
- 普通行政子部门不自动继承工序段，避免“针车办公室”进入派工候选。

### 5.2 派工关系

新增：

```text
order_process_assigned_departments
├─ id
├─ tenant_id
├─ order_process_id
├─ department_id
└─ created_at
```

约束：

```text
UNIQUE(order_process_id, department_id)
INDEX(tenant_id, department_id)
FOREIGN KEY(order_process_id) → order_processes.id
FOREIGN KEY(department_id) → departments.id
```

同一个工序段保存时，该段下全部 `OrderProcess` 共享同一组部门目标，保持当前段级派工语义。

### 5.3 WorkLog 部门快照

给 `work_logs` 新增：

```text
department_id BIGINT NULL
```

写入规则：

- 普通个人报工：取实际计薪员工报工时的 `department_id`；
- 代理报工：取实际受益员工的部门，不取操作人的部门；
- 集体报工：主 `WorkLog.department_id` 取发起人或指定执行部门；每位参与人的工资仍由 `WorkLogGroupShare.worker_id` 记录；
- 历史员工调部门不回写旧 `WorkLog.department_id`。

原 `WorkLog.group_id` 迁移后停止写入，最终删除；`group_detail` 若仅承载参与人分摊则迁入或继续由 `WorkLogGroupShare` 承担，不再表达固定班组。

### 5.4 最终删除

完成迁移和验证后删除：

```text
teams
team_members
order_process_assigned_teams
order_processes.assigned_group_id
work_logs.group_id
```

同时删除对应 SQLAlchemy 模型、关系、服务和兼容分支。

## 6. 派工候选算法

输入：`tenant_id + segment_id`

1. 找出所有启用、`is_production_unit=true`、工序段匹配的部门；
2. 如果某生产部门存在启用且同段的生产后代，则父部门不作为默认候选；
3. 返回最末级生产部门，按组织树顺序排列；
4. 如果某段只有一个候选，页面自动选中；
5. 如果某段有多个候选，允许勾选一个或多个；
6. 没有候选时禁止保存，并提示去组织架构补生产部门，而不是生成默认组。

示例：

```text
裁断段：裁断部                      → 候选：裁断部
针车段：针车部/针车一组/针车二组    → 候选：针车一组、针车二组
成型段：成型部                      → 候选：成型部
```

父部门仍可以通过管理员的“派到整个部门”高级操作被显式选择；此时包含所有后代员工。日常派工页只显示末级候选，避免父子同时出现造成重复选择。

## 7. 派工接口

### 7.1 候选接口

```http
GET /api/v1/departments/dispatch-candidates?segment_id={id}
```

返回：

```json
{
  "items": [
    {
      "id": 21,
      "name": "针车一组",
      "parent_id": 8,
      "parent_name": "针车部",
      "process_segment_id": 2,
      "path": ["生产部", "针车部", "针车一组"]
    }
  ]
}
```

### 7.2 段级派工

沿用接口地址，替换请求字段：

```http
PATCH /api/v1/executions/headers/{header_id}/dispatch-by-segment
```

```json
{
  "assignments": [
    {"segment_id": 1, "department_ids": [7]},
    {"segment_id": 2, "department_ids": [21, 22]},
    {"segment_id": 3, "department_ids": [9]},
    {"segment_id": 4, "department_ids": [10]}
  ]
}
```

校验：

- 部门存在、启用并属于当前租户；
- 部门为生产节点；
- 部门工序段与提交段一致；
- 同一段不可重复提交；
- 一次保存使用单事务，任一段失败全部回滚；
- 空 `department_ids` 表示清除该段派工；
- 主派工页面保存时默认要求所有可执行段至少选择一个部门。

### 7.3 工序输出字段

新增并替代：

```json
{
  "assigned_department_ids": [21, 22],
  "assigned_department_names": ["针车一组", "针车二组"],
  "assigned_department_name": "针车一组、针车二组"
}
```

`assigned_group_id/name/ids/names` 只在一个过渡版本中作为只读兼容别名，随后删除。

## 8. 报工与任务可见范围

### 8.1 普通报工

校验顺序：

1. 存在个人细派时，按个人细派名单校验；
2. 存在部门派工时，检查实际计薪员工是否属于任一目标部门范围；
3. 无任何派工时，继续服从租户的 `allow_unassigned_report` 设置；
4. 工位、主码、工序匹配等现有闸门保持不变。

部门范围判断：

```text
worker.department_id == assigned_department_id
或
worker.department_id 是 assigned_department_id 的启用后代
```

错误文案：

```text
针车工序已派给“针车一组”，张三不属于该生产部门
```

### 8.2 集体报工

- 不再要求存在固定班组；
- 参与人优先使用本次明确选择的 `member_ids`；
- 未明确选择时，可从已派部门范围内选择员工，但不得静默把整个部门全部计薪；
- 最少两名有效计件员工；
- 每个人的数量、单价、工资继续写入 `WorkLogGroupShare`；
- 生产进度仍只增加一次，不按参与人数重复累加。

### 8.3 首页和任务列表

- 员工可见工序段只取本人部门及其祖先对应的工序段；
- 员工可见任务取派给本人部门或祖先部门的任务；
- 负责人可见范围取本人负责部门及全部后代部门；
- 删除“部门归属 ∪ 所在班组段”的并集逻辑。

## 9. 部门负责人、生产组长与权限

组织实体统一不等于人员职责合并。系统保留两种明确角色：

### 9.1 部门负责人

来源：`Department.manager_employee_id`

- 负责行政管理、段级派工、人员调动和部门汇总；
- 负责父生产部门时，可查看和管理全部后代生产部门；
- 可以不属于末级生产组，不计入组内生产人数和默认报工成员；
- 不因为是负责人而自动获得生产组长的代报权限；
- 一名员工可以负责多个部门。

### 9.2 生产组长

来源：`Department.production_leader_id`

- 负责现场带班、查看本组任务、组织集体报工和处理本组异常；
- 必须是该生产部门的在职员工，即 `employee.department_id == department.id`；
- 作为实际生产员工，可以正常报本人产量和计件工资；
- 只管理本人带领的生产部门，不自动覆盖兄弟组；
- 一名员工原则上只带一个末级生产组；如确需兼任，可允许多个部门引用同一人，但必须显式配置。

### 9.3 权限范围

- 管理员、生产经理：跨部门派工和查看；
- 部门负责人：本人负责部门及全部后代部门；
- 生产组长：本人带领的生产部门；
- 普通员工：本人所属部门的任务和本人报工；
- 部门负责人如果也需要参与生产，应当同时属于具体生产部门并正常报工，不能因为管理身份自动产生计件工资。

替换服务：

```text
team_service.is_leader              → department_service.is_production_leader
team_service.is_team_scoped         → department_service.is_department_scoped
team_service.assert_workers_in_scope → department_service.assert_workers_in_scope
```

移动端“我的班组”改为“我的部门”：

- 查看本部门员工；
- 生产组长可以查看本组员工，但正式调入、移出由部门负责人或有员工管理权限的人执行；
- 调入另一个部门的员工必须二次确认，因为这是正式组织调动；
- 不再提供一个员工同时加入多个组的操作。

权限清理：

- 删除 `menu.teams`、`btn.teams.write`；
- 删除班组管理菜单；
- 部门维护统一使用部门权限；
- 删除 `enable_teams`、`team_label` 组织设置及相关前端开关。

## 10. 前端方案

### 10.1 组织架构

员工管理页左侧部门树继续作为唯一维护入口：

- 新建/编辑部门增加“生产部门”开关；
- 开启后选择工序段；
- 在生产部门下新增生产子部门时默认继承工序段；
- 表单分别显示“部门负责人”和“生产组长”，候选范围和权限说明分开；
- 生产组长候选只显示当前生产部门内的在职生产员工；
- 两个字段不默认复制、不联动覆盖；
- 树节点可显示轻量工序段标签；
- 不显示隐形默认组、组长人数等重复信息；
- 员工列表始终按当前部门节点筛选。

### 10.2 派工弹窗

- 标题仍为“生产派工”；
- 工序段横向排列，文字在步骤圆点上方；
- 每个工序段下显示派工部门；
- 单候选自动选中，呈现为已下发状态，不显示多余复选卡；
- 多候选使用紧凑复选项，可同时选择多个子部门；
- 文案全部从“班组”改为“部门/生产组”或中性“派工”；
- 底部提示为“还有 X 个工序段未派工”；
- 主按钮为“保存派工”。

示例：

```text
裁断            针车                  成型            包装
  01 ─────────── 02 ───────────────── 03 ─────────── 04
裁断部          □ 针车一组            成型部          包装部
已选择          □ 针车二组            已选择          已选择
```

### 10.3 报工端

- “我的班组”改为“我的部门”；
- “班组任务”改为“部门任务”或“生产任务”；
- 集体报工显示“参与人员”，不显示固定班组；
- 线产量报工若负责人管理多个子部门，先选择执行部门，再选择参与人。

## 11. 排产与产能

排产的工序段产能改为从生产部门树汇总：

- 活跃人数：统计该工序段所有启用生产部门下的在职计件员工；
- 同一员工只有一个部门，因此不会因多班组关系重复计数；
- 派工负荷按 `assigned_department_id` 聚合；
- 父部门看板汇总所有后代生产部门；
- 现有工序标准产能、个人实绩回退和排产算法不改变。

原 `team_assign_mode`、`team_id` 等排产建议字段改成 `department_assign_mode`、`department_id`；如果只是展示性提示，可直接统一为“生产单元”。

---

## 12. 工资与统计

工资主链不变：

```text
WorkLog.worker_id
+ WorkLog.unit_price
+ WorkLogGroupShare（集体拆分）
→ 工资结算
```

部门只作为统计快照：

- 员工工资：按 `worker_id`；
- 部门产量/人工成本：按 `WorkLog.department_id`；
- 工序段产量：按 `WorkLog.segment_id`；
- 历史“班组产量”报表改名为“生产部门产量”；
- 不允许通过员工当前部门反查并重算历史部门报表。

## 13. 数据迁移

迁移脚本建议命名：

```text
scripts/migrate_teams_to_departments.py
```

脚本必须幂等，并输出迁移报告。

### 13.1 迁移映射

对每个租户：

1. 所有挂有 `process_segment_id` 的现有部门标记 `is_production_unit=true`；
2. `Team.is_default=true`：直接映射到 `Team.department_id`，不创建同名子部门；
3. 普通 `Team`：
   - 在其所属部门下查找同名子部门；
   - 不存在则创建同名生产子部门；
   - 继承 `segment_id`，将 `leader_worker_id` 写入子部门 `production_leader_id`；
4. `TeamMember`：把员工 `department_id` 调整为映射后的子部门；
5. `OrderProcessAssignedTeam`：转换为 `OrderProcessAssignedDepartment`；
6. `OrderProcess.assigned_group_id`：转换后清空；
7. `WorkLog.group_id`：按班组映射回填 `WorkLog.department_id`；无组报工按员工当时可推断部门回填，无法可靠推断则保留空并写入迁移报告；
8. 去重同一工序映射到相同部门的派工关系。

负责人迁移规则：

- 原 `Department.manager_employee_id` 原样保留；
- 原普通班组的 `Team.leader_worker_id` 迁入对应子部门 `production_leader_id`；
- 原隐形默认组若只是由旧同步逻辑复制部门负责人，不自动认定为生产组长，迁移报告列为“待确认生产组长”；
- 原 `Department.leader_id` 只有在该员工确实属于当前生产部门时才迁入 `production_leader_id`，否则保持空并列入待确认清单；
- 迁移后永久删除负责人到组长的自动同步逻辑。

### 13.2 冲突处理

脚本遇到以下情况不得静默覆盖：

- 班组没有部门或工序段；
- 班组工序段与部门工序段不一致；
- 同名子部门已存在但属于其他工序段；
- 班组成员当前属于另一个非父级生产部门；
- 历史班组派工找不到班组记录；
- 历史报工无法推断部门。

处理原则：

- 可唯一推断的自动修复；
- 无法唯一推断的记录到 CSV/JSON 报告；
- 测试租户允许明确参数 `--accept-conflicts` 采用班组归属覆盖；
- 默认模式有冲突则退出且不提交事务。

## 16. 风险与对策

### 风险一：员工临时跨组支援

对策：任务可派多个子部门；特殊情况使用个人细派；集体报工明确选择实际参与人。正式组织归属不因一次支援改变。

### 风险二：派到父部门后范围过大

对策：日常候选只显示末级生产部门；派到父部门放入高级操作，并在保存前提示覆盖范围。

### 风险三：员工调部门影响历史统计

对策：`WorkLog.department_id` 保存报工时快照，历史统计不得使用员工当前部门反推。

### 风险四：旧班组成员与部门归属冲突

对策：迁移脚本先审计后提交；默认有冲突即停止，测试租户才允许显式覆盖。

### 风险五：移除班组后集体计件失去载体

对策：固定班组与一次集体报工拆开；集体报工的真实载体是 `WorkLogGroupShare` 参与人明细，不依赖长期 Team。

## 17. 实现拍板

本次实现按以下结论执行：

1. `Department` 是唯一生产组织实体；
2. 子部门承担生产分组，不再新增平行 Team；
3. 部门负责人使用 `manager_employee_id`，生产组长使用 `production_leader_id`，两者不自动同步；
4. 段级派工目标改为一个或多个 Department；
5. 报工权限按部门树范围判断；
6. 报工和工资继续落到实际员工；
7. 集体报工使用当次参与人，不依赖固定班组；
8. 先迁移引用和停写，再物理删除 Team 相关表；
9. 当前测试数据允许快速切换，但不跳过迁移校验和全量测试。

# 排产人力建模 · 分析笔记（报工反推版）

> **用途：** 回答「排产有没有考虑有多少人能排」——基于四条领域事实（无打卡、只有报工、员工职位字段、班组强制）的二次分析。**决策用，本次不动代码。**
> **定界：** 只分析 `app/services/schedule_engine.py` 的人力维度；不涉及报工/考勤模块本身的设计。
> **关联：** 排产主稿 [`aps-dev-review.md`](./aps-dev-review.md)（状态空间：一期 工单×工序×日；机台/班组/模具×小时 为未来态）。**A' 档实现设计（后端+前端）见 [`schedule-workforce-actual-capacity.md`](./schedule-workforce-actual-capacity.md)。**

---

## 一、领域事实（本轮确认，方案由此推导）

| 事实 | 代码依据 | 对排产的意义 |
|---|---|---|
| **没有打卡/考勤模块** | models/services 无 attendance 相关 | "人力日历"数据源不存在；在岗只能靠报工反推 |
| **只有报工** | `work_logs`：`worker_id × process_id × order_id × qualified_qty × created_at` | 实际人力与产能的唯一事实源 |
| **员工有职位字段** | `Employee.position_id → positions`（工种：针车/成型/…），但 Position 目前只有名字，**无 process 映射** | 技能信号已存在一半，缺"职位→工序族"映射主数据 |
| **班组强制** | `team_members` 唯一约束 `uq_team_members_worker`（一人一组） | 班组数据**完备**，无覆盖率风险，B 档最大数据障碍消失 |

**一个重要陷阱（已核实）：** `work_logs.group_id` **不是班组 id**，而且**系统里根本没有 `groups` 表**——`group_id` 是 `BigInteger`、无外键约束，指向 `work_logs` 自己：集体报工时把同批次拆出来的 N 条个人记录串起来，取**首条 log 的 id**（`report_service.py` L677：`group_id = logs[0].id`），个人报工为 `None`。字段名叫 "group" 只是"组报工"的"组"，与 `teams`（班组）是两码事。所以报工反推必须走 **`work_logs.worker_id → team_members`** 归组，绝不能依赖 `group_id`。

---

## 二、现状核实（一句话 + 公式）

排产里的"人"目前只是工序上的静态工艺定额：

```
工序日产能  = 单人日产能 × 标准人力        (_daily_capacity, L507)
工序天数    = ⌈数量 ÷ (单人日产能 × 标准人力)⌉  (_calc_days, L236)
```

`standard_workers` 写死不随现实变化；engine 不读 `Team`/`TeamMember`；无效率系数、无技能矩阵。详见上一版分析（§现状核实）。

---

## 三、报工数据能推出什么（核心价值）

| 数据源 | 能推出 | 口径 |
|---|---|---|
| `work_logs` 近 N 天按 (process × worker) 聚合 | **实测人均日产量**（含效率、含爬坡） | 合格量÷报工人次（按天去重） |
| 同上 | **活跃人数**（该工序最近真在干的人） | 近 N 天报过工的独立 worker 数 |
| 实测 ÷ 标准 | **效率比**（自动替代论文里 85% 的拍脑袋） | P/Q，直接可展示 |
| `team_members` | **班组实有人数**（完备） | 一人一组，无歧义 |
| `position → 工序族`（待补） | **技能信号**：谁（哪个班组）能干什么 | 工种粒度够粗，匹配粗排粒度 |
| 同工序族实测均值 | **新款产能先验**（无史新款排产的初始值） | 针车新款 ≈ 针车族近 N 天实测人均 |

## 四、方案（报工反推版，取代原 A/B/C）

### A' 档：实测产能优先，配置兜底（建议直接做，已升级为款级聚合）

```
工序日产能 = 该款×该工序近N天实测人均 × 款级活跃人数  （款级有史，复杂度自动内含）
          = 该工序近N天实测人均 × 工序级活跃人数      （款级无史回退）
          = 单人日产能 × 标准人力                     （工序级无史回退，即现状）
```

- **改动面：** `_process_capacity_map` / `_calc_days` / `_daily_capacity` 前加一层聚合：`work_logs` 按 `(process_id, own_product_id, worker_id)` 近 N 天统计（`work_logs.own_product_id` 已存在，零新主数据；复用 `salary_service` / `progress_service` 已有的 WorkLog 聚合模式，可抽公共函数）。
- **天然解决四个缺口：** 效率系数（实测含效率）、缺人（活跃人数随报工波动）、老款爬坡（实测均值本身就是爬坡后的数）、**复杂度（款级聚合后，女鞋/运动鞋同一工序的产出差异自动进产能）**。
- **"谁能干这道工序"= 近 N 天在该工序报过工的 worker 集合**（报工历史即技能证据），按 `team_members` 归组得班组分布——**不需要 Position 映射**，B' 相应缩水。
- 详细设计见 [`schedule-workforce-actual-capacity.md`](./schedule-workforce-actual-capacity.md)。

### B' 档：缩水为"款×工序产能配置"（可选增强，紧随其后）

- **报工历史已回答"谁能干"，B' 不再做 Position→工序映射主链路**；只剩两个可选增强：
  - **新款产能先验：** `own_product_labors` 加"该款该工序单人日产能"（或标准分钟），新款无史时用款级配置 > 工序级实测 > 工序级标准——比回退"配置标准人力"更接近现实，也接回论文的 SAM 模型。
  - **冷启动兜底：** 新人/无报工史人员才需要职位归属；若做，必须给 `positions` 加 `process_id` 字段，**严禁名字字符串匹配**。
- **改动面：** `own_product_labors` 加字段 + masters API；engine 回退链加一层款级配置。
- **前置：** 主数据达标（报工覆盖率高时甚至可跳过本档）。

### C' 档：明确砍掉"人力日历"

- 没有打卡，**做不到"明天精确在岗"**——报工只有历史，请假/加班是未来事件。
- 未来人力口径只能是：**历史均值（A'/B'）+ 手动覆盖值**（PMC 知道明天针车缺 10 人，填一个覆盖数，即原 A 档的兜底逻辑）。
- 结论：**C 档（人力日历）不做**，降级为 A' 的"手动覆盖"按钮。原 C 档论文模型（在岗×工时×效率）在无打卡前提下不可落地，明确写进分期话术，别对客户承诺。

## 五、建议

1. **A' 档直接做**（半天~1 天）：报工反推实测产能（款级聚合）+ 配置兜底，缺人/效率/爬坡/复杂度四个缺口一次解决。
2. **B' 档第二步（缩水版）**：报工历史已回答"谁能干"，B' 只剩"款×工序产能配置"（新款先验）+ 冷启动 Position 兜底，主数据达标后再做。
3. **C' 档明确砍掉打卡依赖**，未来人力 = 历史均值 + 手动覆盖。
4. **排产 UI 口径（任意档都带）：** 工序 X｜班组 Y：实有 **N** 人，近 7 天报工 **M** 人 × 人均 **P** 双（标准 Q，效率 **P/Q**），排产按 **K** 人 × **R** 双/天。一行字让 PMC 看到系统假设与现实的差距，也能发现覆盖值忘改。

## 六、OPEN 项（决策时确认）

1. **Position 映射做不做（B' 冷启动兜底才需要）：** 报工历史已覆盖"谁能干"，新人/无史才用职位归属；若做，`positions` 加 `process_id` 字段（建议映射到"工序族"而非单个工序，鞋厂工种与工序一对多），严禁名字字符串匹配。
2. **报工窗口参数：** 近 N 天取 7 还是 14；"无史"判定阈值（该工序多少天没报工算无史）；活跃人数是否按天去重后取均值而非直接取最近一天（避免某天全厂停工导致误判缺人）；款级与工序级阈值分开配（款级数据稀疏，阈值应更严）。
3. **`position_id` 可空：** 没填职位的员工是否计入班组人力？建议计，但技能信号标记为"未知"，不进 B' 的班组可承担集合。
4. **新款先验的口径（B'）：** `own_product_labors` 加款×工序单人日产能后，新款排产 = 款级配置 > 工序级实测 > 工序级标准；报工达到 ≥3 人天后切换本人实测。
5. **手动覆盖值（原 A 档）保留与否：** 报工反推对"未来缺勤"无感，PMC 需要覆盖入口——确认 UI 入口放哪（排产方案卡 vs 工序档案）。
